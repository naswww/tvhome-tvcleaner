# 00 · 总览与结论速查

## 要解决的问题

一类国产安卓电视（Android 9 / 32 位 / 无 root / 约 1.5 GB RAM）上，
手机端视频客户端播放十几秒就自动退出、卡死，严重时触发框架层软重启甚至整机重启；
同时原厂桌面与预装服务常驻，可用内存被长期占用。

常见误判是「内存不够」或「应用不兼容」，于是反复清理内存、反复重装，问题依旧。
本仓库的做法是：**先把崩溃证据拿全，再逐个拆分变量做对照复现**，最后才改配置。

## 结论速查表

| # | 结论 | 证据强度 | 详见 |
| --- | --- | --- | --- |
| 1 | 起播崩溃是 **native 层**，不是 Java ANR，也不产生 ANR trace | 高（tombstone 直接证据） | `01` |
| 2 | 崩溃栈**至少 4 条互不相同**（OMX 回调 / GPU Surface / 音频消费 / ART odex） | 高 | `01`、`09` |
| 3 | 单一「清内存」无法避免崩溃；可用内存充裕时仍崩 | 中高（对照复现） | `09` |
| 4 | 崩溃常发生在**广告阶段**，正片还没开始 | 高（截图 + 时间线） | `09` |
| 5 | **禁止对视频客户端做全量 AOT**；`speed` 下连续起播全崩，回退 `speed-profile` 后连续完整播放 | 中高（3 次 vs 3 次，见局限） | `05` |
| 6 | 第三方应用收不到 `BOOT_COMPLETED`，持久化 Job 重启后不恢复 | 高（多次重启验证） | `02` |
| 7 | 可用自启通道：`NotificationListenerService` + `BOOT_COUNT` 门控 | 高（连续多次重启验证） | `02` |
| 8 | 本机 oat/odex 与运行时 ART 存在一致性问题，属**系统级**而非单个应用 | 中高 | `05` |
| 9 | 解码策略由服务端在线配置下发，本地 UI 无软解开关 | 高（设置页 + 资源 + 配置日志） | `06` |
| 10 | `/vendor` 媒体配置只读，无 root 无法把厂商硬解翻转为软解 | 高 | `06` |
| 11 | 厂商 wrapper 库依赖缺失 → 固件组件残缺，无 root 补不了 | 中（依赖表 + 加载失败日志） | `06` |
| 12 | 清理器必须保留自建桌面在白名单，否则深度清理会把桌面停掉 | 高（复现并修复） | `04` |

> ⚠️ **最重要的一条**：早期文档里曾把 `cmd package compile -m speed -f <pkg>`
> 当作「优化手段」。这是**已被证伪的错误结论**，会让播放立刻崩溃。
> 终态必须保持 `speed-profile`。详见 `docs/05-dexopt-aot.md`。

## 证据等级定义

| 等级 | 含义 |
| --- | --- |
| 高 | 有 tombstone / 系统状态 / 多次重启验证等直接证据，且可复现 |
| 中高 | 有对照复现数据，但样本量小或存在时间上的混杂因素 |
| 中 | 依赖间接证据（依赖表、日志推断），未做反转验证 |
| 推测 | 仅基于现象相关性，公开时不得当作结论 |

## 工作原则

- **先取证，后改动**；每次只改一个变量，改完立刻验证
- **先保住 ADB**（优先有线网络），再动默认桌面和预装包
- **每一步都有回退命令**，且回退路径本身要先验证可用
- 保留原始证据在本地，**不把设备指纹、日志原文、账号信息带进公开仓库**
